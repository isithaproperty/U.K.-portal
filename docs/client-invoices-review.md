It does not reuse resident service charges, contractor invoices, bank reconciliation, supplier settlements or their invoice numbers.

## User workflow

1. Open **Client invoices**, choose an authorized block, and create a new draft.
2. Configure the issuer name, address, optional company registration number, required supplier contact email or phone at review, client name/address/contact details, explicit invoice type and supply date (plus tax point for VAT), billing period, invoice/due dates, optional purchase reference, payment instructions and notes.
3. Add up to 50 lines with description, quantity (three decimal places), net unit price in GBP (two decimal places) and explicitly reviewed VAT rate (two decimal places). Invoice type starts unselected and must be chosen before review; no VAT rate is populated. An unregistered issuer cannot charge VAT; enabling registration requires a number before review and does not populate any rate automatically.
4. Save the draft. It has a UUID and revision, **no final invoice number**, and a draft-marked PDF. Incomplete drafts may be saved but cannot be reviewed or issued.
5. An owner or admin explicitly confirms the exact saved revision and reviews it. Saving subsequent edits returns it to Draft and removes the review approval. A scoped manager can prepare drafts but cannot review, issue or void them. Review and issue are role-restricted explicit steps; the same owner/admin may perform both, so a mandatory two-person policy is not enforced.
6. An owner or admin explicitly issues the reviewed revision. A distinct, stable `MCI-00000001`-style number is allocated in the same transaction as the frozen issued record and audit event. Issuing is separately gated off by default in the database. No email, resident charge, supplier payment, account posting or receipt is generated.
7. Issued content cannot be edited. An owner/admin may void an issued invoice with a reason; its number and issued audit snapshot remain. There is no deletion workflow or automatic credit/refund. Download either the current PDF or a historical saved revision, including the original issued revision after voiding.

The register is paginated at 25 invoices; audit history loads 20 revisions at a time with older-history navigation. No list total is presented as an outstanding receivable balance. Delivery and payment receipt status are explicitly untracked.

## Database and permission design

- New `public.client_invoices` stores a frozen block/issuer/client/document snapshot, independently calculated integer-pence totals, lifecycle metadata and revision.
- New `public.client_invoice_events` records every Save/Review/Issue/Void, authenticated actor UUID/email, timestamp, exact request UUID/payload and complete resulting snapshot. Authenticated user clients have scoped SELECT only on both tables. No direct INSERT, UPDATE or DELETE grant is provided. Explicit revocations remove all privileges from anon and service_role on the new invoice/audit/configuration tables and both sequences, overriding production-style defaults. The privileged service-role key cannot bypass the audit capability for these new objects.
- RLS permits owners/admins and the current block's scoped manager to read. Residents, contractors, anonymous users and other portfolio managers cannot read or mutate these records. No public share or email link is created.
- A narrow private, explicitly authorized SECURITY DEFINER capability performs lifecycle writes atomically. service_role is explicitly denied execution on the new helpers and public/private mutation functions; only authenticated user clients use the guarded workflow. Its public RPC wrapper is SECURITY INVOKER. Every function has an empty search path; default PUBLIC/anonymous function execution is revoked. Request actors derive from authenticated JWT identity and `portal_members`, never editable user metadata.
- Invoice row/advisory locks, revision checks and globally unique request UUIDs make retries idempotent and reject conflicting/stale actions. Reusing a request with another payload is rejected. Only Issue can use the new private number sequence; authenticated users cannot allocate numbers directly. Both the private issue sequence and the public audit identity sequence are explicitly inaccessible to anon/authenticated/service_role. Gaps may occur after rolled-back transactions; existing numbers are never reused or renumbered. The implementation handles numbers longer than eight digits without truncation.
- `private.client_invoice_configuration` is installed with `writes_enabled=false` and `issuing_enabled=false`. The master gate rejects every mutating RPC action, including replay and Void, when writes are off. A shared configuration-row lock is held until transaction completion, so a committed master-disable waits for in-flight mutations. A CHECK constraint prevents enabling Issue while writes are off. The table has no application grants. Separately, `LONDON_CLIENT_INVOICES_ENABLED` defaults off and only controls the UI/application APIs; it is not a direct-RPC gate. No switch is enabled in production by this work.
- The database independently validates issuer/client structure, dates, positive reviewed lines, limits, VAT registration and rates, and rounds net/VAT per line using integer arithmetic. Caller-supplied totals, lifecycle state, number, actor and timestamps cannot be injected. Stored text must be canonical under the ECMAScript trim-whitespace set; required whitespace-only text, whitespace inside contact emails and noncanonical UUIDs are rejected independently by SQL. TypeScript performs the same calculations for preview and checks saved totals when building a PDF.
- Issued/voided documents preserve their original data; PDFs are deterministic, inert version-1 output derived from saved snapshots, with a SHA-256 response header. Historical revision links remain available. PDF files are not emailed or stored in a separate bucket by this feature.

4. Verify the new objects, RLS, function ACLs, empty search paths, private sequence access and empty client-invoice register. Confirm `writes_enabled=false` and `issuing_enabled=false`. Review Data API exposure of the two public tables and RPC. Keep resident/supplier records untouched.
5. After separate application-release approval, deploy the tested application while `LONDON_CLIENT_INVOICES_ENABLED` is absent/false and both database switches are false. The app flag is a visibility/API switch, not database authorization. To expose a read-only register, authorize setting the app flag to `true` while leaving both database gates false.
6. Only after explicit draft/review-write approval, execute `update private.client_invoice_configuration set writes_enabled=true, issuing_enabled=false where singleton;` as the approved database operator. Save, Review and Void are then permitted to the existing authorized roles through either the app or direct RPC; Issue remains blocked. Confirm issuer/client settings, VAT policy, payment instructions, approvers and the dedicated MCI series/start against external existing invoices. No real test invoice is needed for smoke checks.
7. Only after a further issuing activation approval, execute `update private.client_invoice_configuration set issuing_enabled=true where singleton;`. The database CHECK requires writes_enabled to be true first. Users must still save, review and explicitly issue each invoice. Nothing is sent or posted to other ledgers automatically.
8. For rollback/freeze, first execute `update private.client_invoice_configuration set writes_enabled=false, issuing_enabled=false where singleton;` in one statement. Turning off writes alone while Issue is on fails the CHECK, so use the exact combined statement. The update waits for shared gate locks held by in-flight mutations; after it commits all further mutation RPCs, including replays and Void, are blocked. Scoped SELECT/PDF audit reads remain possible when the app is available. Turn off the app flag and restore the prior application deployment if required. Preserve tables, counters and history; do not drop, truncate or renumber records.

## Risks and limits for review

- A real Issue action creates a finalized outbound invoice record only while both database gates are enabled. The independent app flag must be enabled to use the UI/APIs; direct RPC never depends on that environment variable. There is no automatic email, payment collection, receipting, debtor balance, ledger integration or recurring billing job.
- The issuer/VAT registration number and rates are explicitly configured, not verified against a tax registry. No VAT registration or standard rate is assumed. GBP only; refunds/credit notes, non-block invoices, tax-return reporting and advanced tax treatments are outside this implementation. Finance should approve numbering, tax treatment and document wording before activation.
- An invoice belongs to one existing block for permission scope. The client is a freeform billing snapshot; it is never inferred from a resident or contractor account. Issuer/client data is copied per invoice, not maintained as a separate shared customer directory.
- The built-in PDF font supports Western European text. Unsupported characters block review/issue rather than producing a corrupt issued document. Version-1 rendering must remain available for historical snapshots. There is no archived external PDF storage or malware/content scanning service.
- Audit data retains client billing/contact details. Application users cannot edit/delete audit rows, but database administrators retain their normal privileged access. Retention/access policy needs the same review as other billing data. Existing block deletion is restricted by the invoice foreign key, preserving records.
- The local tests cover revision-collision attempts on a serialized embedded connection; a multi-connection production load/race test and signed-in browser acceptance remain rollout checks. Uncertain requests are retained for exact retry while the current screen remains open; after leaving/reloading, inspect the saved register/audit history rather than recreating invoices blindly.
