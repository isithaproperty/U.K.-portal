## Normal portal integration

The existing manager sidebar opens Management review with live scoped portfolio props. Work-order owners can open the creditor workflow directly; direct arbitrary new Paid updates are blocked. Normal Communications uses the new contact registry and retains legacy resident audiences explicitly. Normal overview displays persistent internal consultation alerts. Debtors shows recorded demand/reminder history and last sent dates. Existing tenant/authentication flows and ledger importer are retained.

The development-only `/review` route is a separate synthetic demonstration and suppresses persistence and posting requests. It is not an authentication bypass for the portal and returns 404 in production even when its preview flag is present.

## Reliability and permissions

- Manager endpoints verify current identity, role and exact block scope, then validate unit/WO membership. State saves use optimistic revisions and append-only history.
- Authenticated clients cannot directly insert delivery rows or invoke the service queue, bypassing document/Section 20 checks. Only the validated server path can queue approved snapshots.
- Approval binds recipients, source revisions, exact bytes and normalized scheduled time. Superseded sources or changed recipients/manager scope are invalidated before sending. In-flight source edits are blocked until outcome review.
- Claims are atomic and skip locked rows. Each worker claims one message at a time, has a bounded deadline and throttles requests. A crash/timeout becomes Uncertain and never blindly retries.
- Sent/provider-accepted records are distinct from delivered/bounced evidence. Signed raw-body webhooks have timestamp checks, constant-time verification and durable replay suppression. Events arriving before submission persistence are retained and reconciled.
- The existing general-communication sender durably reserves requests and freezes retry bodies before provider calls. Completed sends are suppressed permanently; uncertain retries outside the provider idempotency window are blocked.
- Supplier settlement tables are read-only to authenticated clients; a tightly scoped private owner-only transaction validates canonical allocations and synchronizes WO status. Legacy Paid metadata remains editable; evidence-bearing financial corrections require separate audited reconciliation.

## Reviewed activation order and exact dependencies

No new credentials or platform protection settings were created or changed. Before deployment, review and apply the following to a non-production London database with all existing London migrations installed:

1. `supabase/management_review.sql` after existing ledger/automatic-number migrations.
2. `supabase/communication_delivery.sql` after existing `resident_communications.sql`; deploy the updated `resident-communication` Edge Function together with this change.
3. `supabase/supplier_settlements.sql` after existing work-order workflow and management state.
4. `supabase/standing_orders.sql` after `bank_reconciliation.sql` and automatic numbering.
5. `supabase/management_dispatch.sql` after management state and existing units/ledger.

The repository follows reviewed SQL scripts. Supabase CLI generation was unavailable in this sandbox; these scripts were executed directly in disposable Postgres. Live Supabase advisors and deployed Edge verification were not run.

Activation remains explicit:

- `LONDON_LEDGER_BATCHES_ENABLED=1`: approved saved bulk posting only.
- Existing server-side `SUPABASE_SERVICE_ROLE_KEY` connection is required for queue/worker operations; never exposed to client code.
- Existing verified sender connection: `RESEND_API_KEY`, `RESEND_FROM_EMAIL`, optional `RESEND_REPLY_TO_EMAIL`. `LONDON_DELIVERY_ENABLED=1` activates provider submissions. No actual key values were inspected.
- A configured provider webhook with `RESEND_WEBHOOK_SECRET` enables verified delivery/bounce evidence at `/api/management-delivery-events`.
- `LONDON_JOBS_ENABLED=1` and a `CRON_SECRET` of at least 20 characters enable `/api/management-jobs`. `vercel.review-cron.json` is an inactive hourly template; it was not installed as live `vercel.json` or scheduled remotely.
- Every standing-order configuration starts disabled and requires lease confirmation before enabling. Actual imported CSV receipts are supported; a direct bank feed is not required or assumed.
- Actual lease shares, landlord/service addresses, lease payment wording, contact/service permissions and legal notice approval must be supplied/verified by management. These are business/legal evidence dependencies, not repository access blockers.

## Reproduce locally

```sh
npm test
npm run typecheck
npm run build
bash tests/run-postgres-review.sh
```

The SQL harness creates and destroys its own Docker container and accepts no live database URL. It uses synthetic fixtures only.

For API/browser tests, start `node tests/helpers/mock-supabase.mjs`, then run Next against only the explicit fake local endpoint documented in the test helper. Run `tests/management-review-api.mjs`, then `tests/management-workflows-api.mjs`. With Chromium CDP on port 9222, run `tests/browser-persistence.mjs`, `tests/browser-review.mjs` and `tests/browser-workflows.mjs`. The expanded API suite seeds the state used by the workflow browser screenshots. See source comments for local-only fake configuration. Never reuse fake test values in a deployment.

Safe fixture-only preview: `LONDON_REVIEW_MODE=1 npm run dev -- --hostname 127.0.0.1 --port 3010`, then `/review`.
