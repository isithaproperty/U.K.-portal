# Budget attachments: private storage and dispatch proposal

## Implemented local workflow

Service charges now collects an explicit initial/later demand choice and approved recipient-safe category summaries in the existing private financial review JSON. The initial demand preview generates a deterministic PDF containing only selected categories and annual schedule totals, labeled for its building and financial year. It requires an exact PDF review checkbox before queueing. Reminders, later demands, credits and account statements do not automatically receive it. Original workbooks, invoice/payment sheets, resident ledgers and manager combined statements are never attached by this workflow.

The PDF bytes and metadata are captured in the existing immutable recipient envelope and source evidence. Saved financial revision changes invalidate the preview token; existing SQL claim checks invalidate stale pending approvals before submission, and its in-flight source guard blocks concurrent edits while sending. The current queue RPC does not itself check source revision atomically; a narrow queue race can record a stale Pending snapshot, which the claim check rejects before sending. No schema, storage policy, credentials, deployment, delivery configuration or live email was changed. Existing database-backed flow requires its existing reviewed schema to be installed.

`lib/budget-attachment.ts` remains an isolated contract for a possible future original-XLSX workflow. It is not connected to application routes or transport. Original-XLSX storage is **not implemented** and transport still rejects XLSX. The proposal below applies only if original-file retention/sharing is later requested and approved; the current summary PDF does not need a new storage bucket or table.

## Clarified scope

The user specified the budget accompanies the first service-charge issue and belongs in Service charges, not Building statement/account statement. First issue is an explicit saved choice for the selected building/year, not inferred from email count. No automatic reruns or sends were added. Summary-only disclosure must be reviewed separately from financial import approval, and exact PDF contents must be reviewed before queueing.

## Proposed workflow

1. Manager selects original XLSX while viewing an authorized building and explicitly selects its financial year (start/end). Local import previews figures only; this is not attachment approval.
2. A separately reviewed private upload endpoint checks authenticated building access using the same database-backed portfolio policy as managementAccess, enforces a 2 MB original-file cap and verifies XLSX archive structure, decompressed-size limits, macros, embedded objects/external links, malware and unexpected content. File extension, MIME or ZIP signature alone are insufficient. Reject unsupported content rather than silently sanitizing/changing the original.
3. Preserve the exact original under an immutable random version/object key. Compute SHA-256 on the server. Never overwrite a file. The workbook's every sheet, hidden content, comments, personal data and financial detail need recipient-safety review. A summary import preview cannot provide this approval. If unsafe for all residents, request a separate resident-safe budget file; keep the manager original private.
4. Store whole-workbook review against the immutable version/hash, building/year, current saved budget revision and authenticated reviewer. Any changed file, selected version, scope or saved budget revision invalidates review. Client-supplied booleans and hashes are not authoritative approvals.
5. At individual-document preview, server resolves exactly one active approved budget for the explicit building/year, verifies its original bytes/hash and adds it alongside the unit-specific document. Missing/ambiguous year, missing/revoked approval or integrity failure blocks dispatch. For a statement spanning multiple budget years, require explicit year selection or a defined multi-year workflow; never choose arbitrarily. Do not attach budgets to credit notes/Section 20 automatically.
6. Show actual original-file download, filename, year, size, version/hash and unit document before approval. Bind previewToken, envelope idempotency key and sourceEvidence to all bytes and immutable budget metadata. Financial details remain scoped to one resident/unit with one recipient per envelope. Require explicit approval to queue.
7. Atomically verify current version, review status and financial revision again while queuing, locking relevant records. A review/update race must not allow a stale approval. Before provider submission, reject or cancel not-yet-submitted jobs whose source approval was revoked/replaced, requiring a new preview; never mutate a queued envelope to use a new file. Already submitted/uncertain items retain exact historical bytes and follow reconciliation rules, not blind resend.
8. Archive superseded originals without deletion or public access. Historical records reference their exact version and preserve captured attachment bytes. Separate historical retention from “currently approved for new sends”.

## Proposed database/storage design (not executable migration)

- Private bucket `budget-originals`, public disabled. Object path is server-generated building ID/version ID/original; do not trust client paths. Use insert-only immutable version writes. No overwrite or delete permissions for normal app flows.
- Version table: UUID primary key, building foreign key, year start/end, saved budget revision, filename, exact MIME, byte length (1–2,000,000), SHA-256, unique immutable object key, uploader identity/time, archive time. Check dates and size; original content cannot be replaced.
- Review table: version foreign key, exact hash, building/year/revision, authenticated reviewer and reviewed time, explicit whole-file recipient-safety decision, revocation time/reason. Avoid treating client-set reviewer strings as identity.
- Active selection table: unique building/year, version reference, monotonically increasing selection revision. Updating selection invalidates unsubmitted approvals. Composite foreign keys/checks ensure selected version belongs to the same building/year.
- RLS on all exposed tables and private storage policies enforce current owner/admin/assigned-manager authorization, matching existing portfolio rules. A signed-in user alone is not authorization. Residents cannot enumerate or download original manager files. Never grant public/anonymous reads. Download endpoints recheck access and return no-store responses; no public URLs or shared caches.
- Queue transaction accepts server-generated attachment snapshot plus version/review IDs, checks all scope and revision bindings under row locks, and records exact metadata in immutable envelope/source evidence. Worker receives only approved queued bytes, not broad authority to list/download originals. No service-role expansion for upload or manager access.
- Limit encoded attachments together to existing 3 MB batch cap, accounting for base64 expansion and unit-document bytes. The 2 MB source cap leaves only approximately 333 KB encoded for other attachments; reject any combined overflow rather than omit the budget.
- Migration must be separately reviewed/approved and tested against isolated fixtures before production. Do not apply this prose as SQL. Use project migration tooling when actual schema work is authorized.

## Required acceptance tests before enabling

Cross-building and cross-year reads/uploads/downloads/queues fail; unauthenticated/unassigned managers fail; unsafe/oversized/non-XLSX archives fail; workbook full-content review is mandatory; replaced budgets or changed saved figures invalidate approvals including concurrent update/queue races; missing budget blocks sends; manager combined statements never enter recipient envelopes; exact per-recipient attachment history survives replacement; worker remains disabled until configuration and delivery authorization are separately verified. Test queued/scheduled revocation and uncertain-send reconciliation. No live resident email for testing.
